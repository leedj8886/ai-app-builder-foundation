## 推荐发布顺序

1. 合并并确认 `main` 的 `Quality`、`Integration`、`Smoke` 全绿。
2. 创建 GitHub Preview Release，使用 Release Notes 草稿并附上演示入口。
3. 先发布 X 或 V2EX，验证链接、图片裁切和安装反馈。
4. 再发布 Show HN 与 Reddit，并根据前一轮反馈修正文案或故障排查。
5. 首日集中记录安装失败、成功启动时间、有效 Issue 和外部贡献。

## 对外表述边界

- 可以说“真实生产构建验证”“可审计 Run”“版本化 Snapshot”“可自托管”。
- 必须说清当前是 Developer Preview；产品导览使用确定性 fixture，失败恢复实录使用受控故障注入和真实 DeepSeek。
- 不要说“一键部署”“适用于生产”“支持任意提示词”“模型输出一定可修复”。
- 不要把 Build Verified 等同于业务正确、安全审计或合规认证。
- 可以说“公开展示了真实 Provider 根据验证诊断完成恢复”，但必须同时说明故障是受控注入，不能描述为模型自然犯错或成功率证明。
